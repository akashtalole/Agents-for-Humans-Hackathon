# BidWright

## Elevator Pitch

An AI agent that takes a small business from "here's an RFP" to "here's a
compliant, tailored proposal draft and a short list of what you still need
to decide" — reading the solicitation, checking your paperwork against every
requirement, and drafting the proposal itself, so the only thing you spend
your own judgment on is the gaps that actually need it.

## Inspiration

Small contractors and service businesses — landscapers, IT shops, cleaning
companies, consultants — lose bids they were qualified to win, not on price
or capability, but on a technicality: a missing certificate, an insurance
minimum that's a dollar short, a page limit nobody noticed. Reading a dense,
repetitive RFP, cross-checking every requirement against your own paperwork,
and writing a tailored proposal is hours of judgment-adjacent busywork —
exactly the kind of work that eats the time an owner should be spending
running the business, or bidding on the *next* contract. None of it is hard;
all of it is unforgiving. We wanted an agent that does the unforgiving part
completely, and only interrupts a human for the part that actually needs a
human: deciding whether a gap is worth fixing, and whether to bid at all.

## What it does

Given an RFP document and a company capability profile, BidWright:

1. **Reads** the RFP (PDF, DOCX, Markdown, or plain text) and the company
   profile.
2. **Extracts** a structured requirements record: deadline, submission
   method, required certifications/licenses, minimum insurance, eligibility
   criteria, evaluation criteria, format rules, and a full submission
   checklist.
3. **Checks compliance**: for every requirement, decides `met`, `gap`, or
   `needs_review`, with a severity (`blocking` vs `warning`) and a concrete
   recommendation for closing each gap. It never claims something is met
   unless the company profile actually backs it up.
4. **Creates a calendar reminder** (`.ics`) for the submission deadline, with
   automatic 3-day and 1-day advance reminders.
5. **Drafts the proposal**: cover letter, executive summary, technical
   approach, qualifications, and a compliance matrix — honestly flagging
   open gaps instead of papering over them. Pricing is left to the owner;
   the agent never invents numbers.
6. **Surfaces exactly one decision-ready summary** (`decisions_needed.md`):
   ready to submit, or here are the *N* blocking gaps and what to do about
   each one. Everything else runs unattended.

Run against the bundled example — a municipal landscaping RFP paired with a
deliberately underinsured example company — it correctly found 8 real
blocking gaps (general liability insurance at $1M when the RFP requires
$2M/$4M, a missing signed cover letter, a missing pricing schedule, and
more) plus 1 non-blocking gap (no ISA-certified arborist on staff, which the
RFP lists as preferred, not required) — exactly the kind of finding a human
reviewing the same two documents by hand would eventually catch, minus the
hour it'd take to get there.

## How we built it

BidWright is a Strands Agents SDK **"agents as tools"** multi-agent system:
an orchestrator agent (`bidwright/orchestrator.py`) decides what to do next,
and each pipeline stage — RFP analysis, compliance checking, proposal
drafting — is itself a full Strands `Agent` call with its own system prompt
and a typed Pydantic structured output (`RFPRequirements`,
`ComplianceReport`, `ProposalDraft` via `structured_output_model=`), wrapped
as a tool the orchestrator can call.

Three design choices we think matter more than they look:

- **Structured contracts, not free text between agents.** Sub-agents return
  validated Pydantic models, not prose the next stage has to re-parse. The
  orchestrator LLM only ever sees short natural-language tool summaries —
  the documents actually written to disk always come straight from the
  validated data, so a chatty orchestrator can never corrupt the numbers
  it's reporting on.
- **The one file a human must read is generated by code, not the model.**
  `decisions_needed.md` is built deterministically from the
  `ComplianceReport` in `bidwright/rendering.py`. That guarantee doesn't
  depend on the orchestrator remembering to keep its promise on any given
  run.
- **Model-provider agnostic by default.** `bidwright/config.py` picks
  Anthropic's API directly (local dev, `ANTHROPIC_API_KEY`) or Amazon
  Bedrock (no key, just AWS credentials — the path AgentCore deployments
  use) automatically, from whatever's present in the environment, and every
  agent in the system shares that one decision.

## Challenges we ran into

The offline test suite (schemas, rendering, tool functions, orchestrator
wiring with sub-agents mocked) passed clean early and stayed clean. The real
problems only showed up against a live model.

The first live end-to-end run took about 40 minutes and then failed. The
orchestrator kept calling `draft_proposal_document` with an empty or
truncated tool-call input, retrying, and eventually got a 400 back from the
Anthropic API. We tracked it down by reading Strands' own streaming code
(`event_loop/streaming.py`): with `max_tokens=4096`, the model's response
was getting cut off exactly as it started emitting the `tool_use` block on
later, more verbose turns — leaving zero characters of JSON input. Strands
logs a warning and silently defaults that input to `{}` and retries, but the
model kept hitting the same ceiling on the retry too, so it looped until the
accumulated malformed tool-call history broke the conversation entirely.
Raising `max_tokens` to 8192 fixed it — and we applied the same fix
preemptively to ClaimClarity's config, since its live run happened to pass
at 4096 but is exposed to the identical failure mode on a longer
conversation.

The second issue was subtler and, we think, more interesting: every
*generated file* (requirements, compliance report, decisions needed,
proposal draft) was correctly grounded in the real input documents on every
live run — but the orchestrator's own free-text final reply, which the CLI
printed as its headline summary, sometimes fabricated specifics that didn't
match the real case: wrong gap names, wrong dollar amounts, once an entirely
invented "MBE/WBE certification" requirement that isn't anywhere in the RFP.
Root cause: the orchestrator's tool functions deliberately return terse
summaries ("8 gap(s) found (3 blocking)") to keep its own conversation
short, but its system prompt then asked it to enumerate each gap "in plain
language, with the concrete action needed to close it" — detail it was
never actually given. The model complied with that instruction the only way
it could: by inventing plausible-sounding specifics. We fixed it two ways —
rewording the prompt to explicitly tell the model it only has counts and
filenames, and to point to `decisions_needed.md` instead of reconstructing
detail from memory; and, as defense in depth, having the CLI and Streamlit
app print/show the deterministic `decisions_needed.md` content as the
trusted headline first, with the orchestrator's own reply demoted to a
clearly-labeled, informational-only view underneath.

## Accomplishments that we're proud of

- The discipline that the one file a human is asked to trust
  (`decisions_needed.md`) never depends on the model's own retelling of its
  work — it's rendered straight from validated structured data, in plain
  Python, every time.
- Finding and fixing both of the bugs above by actually running the system
  against a real model repeatedly, not stopping at "the offline tests pass."
  Neither bug was visible from mocked tests; both were real, and both are
  now covered by regression tests plus an honest paragraph in the docs
  explaining exactly what happened.
- A live run against a genuinely deliberately-flawed example (an
  underinsured landscaping company) that surfaces real, specific, correctly
  reasoned gaps — not a canned happy path.

## What we learned

Terse tool-result summaries can starve a later free-text step of the facts
it needs to do what its own prompt asks of it — and a capable model doesn't
fail loudly when that happens, it fills the gap with confident, plausible,
wrong specifics. The fix isn't "prompt it harder to be accurate," it's
architectural: never let the thing a human has to trust be reconstructed
from memory when it can instead be rendered from the data that's already
sitting there, validated. We also relearned a more mundane but easy-to-miss
lesson: a `max_tokens` ceiling that looks generous for a short response can
silently truncate a tool call on a longer, more detailed turn, and the
failure mode (an infinite retry loop, not a clean error) is much worse than
the truncation itself — worth raising the ceiling and re-testing live
before assuming a limit is safe.

## What's next for BidWright

- Broader document format support (scanned/OCR'd PDFs, spreadsheet-based
  RFP requirement matrices some agencies use instead of prose).
- More jurisdictions and RFP conventions — state and federal solicitations
  have their own boilerplate and terminology beyond the municipal example
  bundled here.
- An actual live run of the Amazon Bedrock AgentCore deployment path
  (`deploy/cloudshell/setup.sh`) against a real AWS account — it's been
  verified as far as offline testing can reach (bash syntax, payload
  shapes) but not exercised end-to-end yet.
- A lightweight review/edit loop in the Streamlit UI so an owner can mark a
  gap "fixed" and re-run just the compliance check, instead of the whole
  pipeline.

## Architecture Diagram

See `architecture-diagram.png` in this folder. It shows the orchestrator
agent driving five tool calls — document loading, RFP extraction, compliance
checking, deadline reminder creation, and proposal drafting — three of which
are themselves full Strands sub-agents writing validated structured output
(`RFPRequirements`, `ComplianceReport`, `ProposalDraft`) into a shared
`BidJob` state, which deterministic rendering code turns into the five
output files, with only the blocking items in `decisions_needed.md`
surfaced back to the business owner.

## Testing Instructions

Full step-by-step instructions are in [`TESTING.md`](TESTING.md) in this
folder. Fastest path: `pip install -e ".[ui,dev]"`, then `pytest` for a
free, offline sanity check (112 tests, no API key), then either
`bidwright run --rfp examples/sample_rfp.md --profile examples/company_profile.json --out output`
or `streamlit run app_streamlit.py` for a real, billed run against the
bundled example (a few minutes, real model calls).
