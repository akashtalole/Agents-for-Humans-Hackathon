# ClaimClarity

## Elevator Pitch

An agent that reads your health insurance denial, checks it against real ICD-10 coding rules and your plan's own terms, and drafts the appeal — or tells you honestly when it's not worth fighting.

## Inspiration

A large share of in-network health insurance claims get denied, and most denials are never appealed — not because they're valid, but because decoding an Explanation of Benefits, figuring out whether the denial reason is even legitimate, and drafting a correctly-argued appeal inside a strict filing window (often 180 days) is a specialized, exhausting task nobody has the bandwidth for while sick, injured, or already stressed about a bill. A lot of those denials are pure mechanical billing errors — an outdated diagnosis code, a typo — that would be reprocessed immediately if someone just caught it and said so. That gap, between "this is fixable in five minutes" and "nobody ever looks," is what ClaimClarity is for.

## What it does

Given a denial notice/EOB (and, where available, a plan summary of benefits and a medical record excerpt), ClaimClarity:

1. **Reads** the documents (PDF, DOCX, Markdown, or plain text).
2. **Extracts** a structured claim record: patient, insurer, claim number, every denied line item with its procedure/diagnosis codes and denial reason (CARC/RARC codes where stated), relevant plan terms, and the appeal deadline.
3. **Creates a calendar reminder** (`.ics`) for the appeal deadline, with automatic 14-day and 3-day advance reminders.
4. **Investigates each denied line item for real** — before concluding anything about a diagnosis code, the investigating agent actually calls an ICD-10 code lookup tool rather than reasoning from a language model's memory of medical coding (a common source of confidently wrong billing advice). Every item is classified as a `billing_error` (mechanically fixable), `documentation_gap` (needs more info from the provider), or `valid_denial` (genuinely excluded — not worth appealing) — each with cited evidence, never a guess.
5. **Drafts the appeal** for everything worth appealing, citing the specific denial reason, the corrected code where applicable, and the plan term that supports coverage — and writes an honest plain-language explanation for anything that isn't worth appealing, instead of drafting a doomed letter just to be agreeable.
6. **Surfaces exactly one decision-ready summary** (`decisions_needed.md`): what's worth appealing, what isn't and why, and the deadline. Everything else runs unattended.

The bundled example demonstrates exactly this: a physical therapy claim (CPT 97110) billed with diagnosis code M54.5 — deprecated for billing purposes in FY2022, a real and common mechanical cause of denials — bundled alongside a massage-therapy line item (CPT 97124) that's a genuine plan exclusion. A real run against this example correctly told the two apart: it classified the PT item as `billing_error`, worth appealing, with the corrected code `M54.51` (Vertebrogenic low back pain), and the massage item as `valid_denial`, not worth appealing — rather than the easy failure mode of just recommending "appeal everything."

## How we built it

ClaimClarity is a Strands Agents SDK "agents-as-tools" orchestrator (`claimclarity/orchestrator.py`) driving three sub-agents through tool calls, sharing state via a validated `ClaimCase` object:

- **`claim_analyzer`** — turns raw documents into a structured `ClaimRecord` (Pydantic model): patient, insurer, line items, codes, denial reasons, plan terms, deadline.
- **`denial_investigator`** — the one sub-agent given real tools, `lookup_icd10_code` and `search_icd10_codes`, and explicitly instructed to call them before making any claim about a diagnosis code's validity. It reasons over a small, curated, cited subset of the FY2026 ICD-10-CM code set (`claimclarity/data/icd10_reference.json`), and the lookup tool says so honestly for any code outside that subset rather than guessing. Output is a validated `DenialFindings` object, never free text.
- **`appeal_drafter`** — turns `DenialFindings` into an `AppealPackage`: a real letter for what's worth appealing, an honest explanation for what isn't.

Every inter-agent handoff is a Pydantic-validated structured object, not free text — the same discipline as this repo's other entry, BidWright. Critically, the one file meant to interrupt a human for a real decision, `decisions_needed.md`, is rendered deterministically from the validated `DenialFindings` in code (`claimclarity/rendering.py`), not generated by the model retelling its own work. `claimclarity/config.py` picks Anthropic direct or Amazon Bedrock automatically depending on available credentials, so the same pipeline runs against either provider. The CLI (`claimclarity run`) and a Streamlit demo (`app_claimclarity.py`) both wrap the same `run_claim_case()` pipeline function, and an optional `agentcore_app_claimclarity.py` wraps it again for Amazon Bedrock AgentCore Runtime deployment.

## Challenges we ran into

Two real bugs, both found by actually running the thing against a live model rather than trusting the offline test suite alone:

**1. An orchestrator hallucination, found during live integration testing.** Every generated file (`claim_summary.md`, `denial_findings.md`, `decisions_needed.md`, `appeal_package.md`) was correctly grounded in every live run. But the orchestrator's own free-text final reply to the user — a separate thing from those files — once fabricated an entirely different, unrelated claim scenario. Root cause: its tool results intentionally carry only counts and filenames back to the orchestrator (not full document contents, to keep context small), but its prompt was asking it to enumerate specifics anyway, so when asked to recap details it didn't actually have, the model confabulated them instead of deferring. Fixed by rewriting the orchestrator's closing instructions to defer to `decisions_needed.md` rather than reconstruct details from memory, and by demoting the orchestrator's own reply in both the CLI and the UI to a clearly-labeled, informational-only view — with the deterministic, code-rendered `decisions_needed.md` shown as the trusted headline instead.

**2. A Streamlit UI threading bug, found while producing this documentation.** The demo's live tool-call log calls Streamlit UI methods (`st.empty().code(...)`) from inside the `callback_handler` passed to the pipeline. Strands' synchronous agent invocation always runs the agent — and therefore always invokes that callback — inside a fresh `ThreadPoolExecutor` thread (`strands/_async.py`'s `run_async`), which never receives Streamlit's `ScriptRunContext`. The result is a deterministic `streamlit.errors.NoSessionContext` crash on the very first tool call, every time, for every user — not a rare race. Full detail, including a captured screenshot of the crash and exactly what the fix would be, is in `docs/claimclarity/screenshots/NOTES.md`. We verified the underlying pipeline itself is unaffected by re-running the same example through the CLI, which is a separate code path whose callback only prints to stdout.

## Accomplishments that we're proud of

- Real ICD-10 grounding via an actual lookup tool, not model memory — the investigator agent's tool trace shows it calling `lookup_icd10_code` and `search_icd10_codes` before it concludes anything, and a live run correctly identified M54.5 as a retired category header and found the specific replacement code M54.51.
- The `decisions_needed.md` discipline: the one artifact meant to interrupt a human for a real decision is rendered by code from validated structured data, never handed to the model to summarize freely.
- Catching and fixing a real hallucination bug through live-model testing rather than assuming 30+ passing offline (mocked) tests meant the system was trustworthy end to end.
- Finding and precisely root-causing a second, unrelated real bug (the Streamlit threading issue above) while producing this very documentation, and being honest about it rather than papering over it with staged screenshots.

## What we learned

- Terse tool-result summaries (counts and filenames, by design, to save context) can starve a model's own final-answer step of the facts it needs — and a model asked to enumerate specifics it wasn't actually given will confidently fabricate them rather than say "I don't have that detail; see the file." The fix isn't "add more instructions to be careful" — it's to not ask the free-text step to do a job that a deterministic renderer should do instead.
- Offline, mocked tests validate wiring and schemas well, but only a real model call exercises the model's own judgment — tool-call ordering, what it decides to say when asked to recall details it wasn't given. Both matter, and neither substitutes for the other.
- A callback pattern that works cleanly for a stdout-printing CLI can be structurally broken for a stateful UI framework like Streamlit, because of how the underlying SDK bridges sync and async execution (a fresh thread per call, unconditionally) — a detail easy to miss until you actually click the button.

## What's next for ClaimClarity

- Swap the curated ICD-10 demo subset for a full, live ICD-10-CM data source (an API or MCP server) so `lookup_icd10_code` can validate any code, not just the ones in the bundled reference file — `claimclarity/tools/icd10.py`'s docstring already documents how.
- Support more insurers' plan-document formats and a wider variety of denial-reason (CARC/RARC) codes beyond the bundled example.
- Fix the Streamlit UI threading bug documented above (`docs/claimclarity/screenshots/NOTES.md`), and verify a real Amazon Bedrock AgentCore Runtime deployment end to end (the `agentcore_app_claimclarity.py` entrypoint and `deploy/` scaffolding exist but a live AgentCore deployment run is still a stretch goal, not something we've verified).

## Testing Instructions

Full step-by-step instructions are in `docs/claimclarity/TESTING.md` in this folder. Fastest path: create a Python virtualenv, `pip install -e ".[dev]"`, then run `pytest` — 30+ tests pass offline with no API key, in a couple of seconds, and exercise the tool functions, Pydantic schemas, Markdown rendering, and orchestrator wiring. To see it run against a real model, set `ANTHROPIC_API_KEY` and run `claimclarity run --document examples/claimclarity/denial_notice.md --document examples/claimclarity/plan_summary_of_benefits.md --document examples/claimclarity/medical_record_excerpt.md --out output` (a few minutes, real billed API calls).
