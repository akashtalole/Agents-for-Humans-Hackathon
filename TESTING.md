# Testing

**507 tests. 504 pass offline with no API key, no network and no cost.** The
other 3 are opt-in live-model tests, skipped by default.

```bash
pip install -e ".[api,dev]"
pytest
```

Expected output:

```
504 passed, 3 skipped
```

If that runs green, the codebase is verified as far as it can be without
spending money. What that does and does not prove is spelled out below.

BidWright is the awkward one because its earliest tests predate the
`test_<project>_*.py` naming convention the other three follow —
`test_calendar.py`, `test_documents.py`, `test_models.py`,
`test_rendering.py` and `test_pipeline_integration.py` are all BidWright's.

A `-k` expression is the wrong tool here: `-k "... or models or rendering ..."`
matches substrings across *every* file, so it also picks up
`test_claimclarity_models.py` and `test_glacierwatch_rendering.py` and
collects 153 tests rather than 113. Select by file instead:

```bash
pytest tests/test_bidwright_*.py tests/test_calendar.py tests/test_documents.py \
       tests/test_models.py tests/test_rendering.py tests/test_pipeline_integration.py
```

## Live integration tests (these cost money)

Three tests make real model calls and are skipped unless explicitly enabled:

```bash
BIDWRIGHT_RUN_INTEGRATION=1    pytest tests/test_pipeline_integration.py
CLAIMCLARITY_RUN_INTEGRATION=1 pytest tests/test_claimclarity_pipeline_integration.py
GLACIERWATCH_RUN_INTEGRATION=1 pytest tests/test_glacierwatch_pipeline_integration.py
```

Each runs that project's full pipeline end to end against a real model, so
each needs credentials configured (see [SETUP.md](SETUP.md#4-configure-model-credentials))
and each will incur API charges. Trinetra has no equivalent gate — its
deterministic core is covered offline and its agent layers are tested with
mocked agents.

## What the offline suite actually verifies

This matters more than the count, so it is worth being precise about.

**Fully verified offline**, because it is deterministic code with no model in
the path:

- Every calculation a safety or money decision rests on. GlacierWatch's risk
  scoring, Trinetra's crowd simulator, its Godavari evacuation-feasibility
  arithmetic, its finite-responder allocation, ClaimClarity's ICD-10 and
  appeal-deadline logic, BidWright's compliance matrix.
- Every guardrail. These are deliberately pure code because they are the last
  thing standing between a model's draft and a consequence — Trinetra's
  rumour-counter-message scan and its A2A peer-reply scan are both tested
  adversarially, with the dangerous phrasings enumerated as parametrised
  cases and the *false-positive* cases pinned too.
- Every deterministic Markdown renderer — the files a human actually reads
  are generated by code, never authored by a model, so their content is
  exactly checkable.
- Calibration against real historical events. Trinetra's simulator is
  replayed against the 2003 Nashik and 2025 Prayagraj crowd-crush incidents
  and must flag both CRITICAL; its hydrology module must reproduce the
  reported severity of two cited Gangapur discharge observations. A model
  that cannot reproduce a documented disaster is not safe to plan with.
- All four FastAPI backends, including draining a live SSE simulation stream
  to completion, with the agent layer mocked.
- Orchestrator wiring, with sub-agents mocked — that the right agent is
  called with the right validated payload.

**Not verified offline**, and stated plainly rather than glossed:

- **Model output quality.** Whether an agent's judgment is *good* is not
  something a test asserts. The live integration tests above exercise the
  real path; everything beyond that was checked by reading actual generated
  output during development, which each project's doc reports honestly,
  including the cases where it was wrong.
- **The AWS deployment paths.** Nothing under `deploy/` has been run against
  a live AWS account. The scripts are syntax-checked, shellcheck-clean and
  dry-runnable, and their CLI parameters are taken from the AWS CLI command
  reference — but no deployment has been performed. Read each directory's
  README before running one.
- **A2A transport against third-party agents.** The protocol handling was
  verified live during development (Trinetra served a real agent card and
  completed a card-resolution → `message/send` round trip, and a deliberately
  hostile stub peer was blocked end to end), but the peers in
  `trinetra/data/a2a_peers.json` are illustrative placeholders — no external
  organisation's agent has been called.

## Conventions used throughout

A few things are true of every test file here, and are worth knowing before
reading them:

- **No test needs an API key or a network connection**, except the three
  opt-in ones above. Agent-calling functions are monkeypatched on the module
  where they were imported, so the deterministic engine under test stays
  real while only the model layer is faked.
- **Tests assert invariants, not transcripts.** Resource allocation is tested
  for "a critical demand is never starved by a lower-severity one regardless
  of input order", not for a specific split of units. That is what makes the
  test survive a refactor and still mean something.
- **Negative and false-positive cases are pinned deliberately.** A guardrail
  that blocks everything is useless, so the tests assert both that a peer
  narrating *its own* actions is not mistaken for one claiming authority, and
  that naming an official channel to trust is not mistaken for promising
  safety.
- **Bugs found in production code get a regression test that names the bug.**
  For example `test_sos_medical_incident_requests_medical_units` documents a
  real defect where an enum was compared against string literals that did not
  exist, making a medical branch dead code so a collapsed pilgrim silently
  raised a police demand instead of an ambulance.

## Continuous checks beyond pytest

```bash
# Shell deploy scripts
bash -n deploy/**/*.sh
shellcheck -S error deploy/**/*.sh

# Frontend type-checking and build (also catches unused imports)
cd webapp/trinetra && npm run build      # and likewise for the other three

# Any deploy script, without touching AWS
./deploy/ecs-express/trinetra/setup.sh --dry-run
```
