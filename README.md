# Agents for Humans Hackathon

Four independent, end-to-end agent systems built with the
[Strands Agents SDK](https://strandsagents.com), each aimed at a real,
specific piece of busywork or risk — or, for GlacierWatch and Trinetra, at
people who actually die when the decision goes wrong.

| | Track | Pitch |
|---|---|---|
| **[BidWright](BIDWRIGHT.md)** | Professional Agents | Reads an RFP, checks a small business against every requirement, drafts the proposal, and only asks you to decide the things only you can decide. |
| **[ClaimClarity](CLAIMCLARITY.md)** | Everyday Agents | Reads a health insurance denial, checks it against real ICD-10 coding rules and your plan's own terms, and drafts the appeal — or tells you honestly when it isn't worth fighting. |
| **[GlacierWatch](GLACIERWATCH.md)** | Good Neighbor Agents | Combines published, cited Himalayan glacial-hazard assessments with live weather and seismic data to prioritise monitoring attention this week. Decision support for disaster-management authorities, never a prediction of an avalanche or flood. |
| **[Trinetra](TRINETRA.md)** | _track not yet declared_ | A multi-agent platform for the Nashik-Trimbakeshwar Kumbh Mela 2027: pilgrim guidance in nine Indian languages, a crowd digital-twin calibrated against two real stampedes, Godavari flood-evacuation feasibility, rumour triage, multi-hazard incident command, and A2A interoperability with other agencies' agents. |

All four share the same architectural discipline:

- A Strands **"agents as tools"** orchestrator.
- **Validated Pydantic structured outputs between every stage** — never free
  text an LLM might restate wrong.
- **A deterministic core, and an LLM interpretation layer on top.** Anything a
  safety or money decision rests on is computed by plain code from cited data;
  models interpret those numbers, they never produce them.
- **A single trusted output** — a Markdown file generated by code, not by the
  model — that is the only thing a human actually has to read.
- **Honest limitations documented in full**, including the things that don't
  work and the numbers that are estimates rather than facts.

Each project is independently runnable, independently tested, and documented
in its own file linked above.

## Quickstart

```bash
python3 -m venv .venv && source .venv/bin/activate
pip install -e ".[api,ui,dev]"
pytest                 # 504 offline tests, no API key, no network, no cost
```

That is the whole verification path — no credentials needed. To make real
model calls:

```bash
cp .env.example .env   # then set ANTHROPIC_API_KEY, or configure AWS for Bedrock
trinetra status        # confirm which provider is active, without a billable call
```

## The interfaces each project ships

Pick whichever suits what you're doing. Trinetra has no Streamlit demo — its
dashboard was built as the React UI from the start.

| | CLI | Streamlit demo | React web UI |
|---|---|---|---|
| BidWright | `bidwright` | `streamlit run app_streamlit.py` | `python server_bidwright.py` |
| ClaimClarity | `claimclarity` | `streamlit run app_claimclarity.py` | `python server_claimclarity.py` |
| GlacierWatch | `glacierwatch` | `streamlit run app_glacierwatch.py` | `python server_glacierwatch.py` |
| Trinetra | `trinetra` | — | `python server_trinetra.py` |

The React UIs are a FastAPI backend plus a Vite/React/TypeScript frontend
served from one process, so there is no CORS setup. **Build the frontend once
before starting a server** (`cd webapp/<project> && npm install && npm run build`)
— see [SETUP.md step 6](SETUP.md#6-build-the-web-uis-optional). Each serves on
port 8000, so run one at a time.

Trinetra additionally ships an **A2A agent server** (`server_trinetra_a2a.py`)
— a machine-facing surface that publishes an
[Agent2Agent](https://a2a-protocol.org/) card other organisations' agents can
discover and call, rather than a human-facing dashboard.

## Deploying to AWS

All deployment is **optional** — every project runs entirely locally. All of it
creates **real, billable AWS resources**, and **none of it has been exercised
against a live AWS account**: the scripts are syntax-checked, shellcheck-clean,
dry-runnable and grounded in the AWS CLI command reference, but no deployment
has been performed. Read the relevant README before running anything, and run
the matching `teardown.sh` when you're done.

Every script supports `--dry-run`, which prints what it would do and touches
nothing.

**→ [deploy/CLOUDSHELL.md](deploy/CLOUDSHELL.md)** — step-by-step instructions
for every path that runs from AWS CloudShell, with prerequisites, teardown and
troubleshooting. Three of the seven paths need local Docker and are called out
there explicitly.

### Bedrock AgentCore Runtime

Two separate directories, both runnable straight from
[AWS CloudShell](https://aws.amazon.com/cloudshell/) with no local install or
Docker:

- [`deploy/cloudshell/`](deploy/cloudshell/) — **BidWright and ClaimClarity**.
  Supports both Bedrock and an Anthropic API key as the model provider; see
  that README's note on how the key reaches the runtime without CodeBuild ever
  seeing it.
- [`deploy/trinetra/`](deploy/trinetra/) — **Trinetra's headless action API**
  (`agentcore_app_trinetra.py`, routing `ask`/`sos`/`simulate`/`calibrate`),
  following the same pattern.

GlacierWatch has no AgentCore path; its only AWS deployment is the ECS Express
one below.

### ECS Express Mode (the web UIs)

Each web UI has its own [ECS Express Mode](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/express-service-overview.html)
path — a managed Fargate service that provisions its own load balancer, TLS
certificate, public HTTPS URL and autoscaling:

| Directory | Deploys | Image built by |
|---|---|---|
| [`deploy/ecs-express/bidwright/`](deploy/ecs-express/bidwright/) | BidWright web UI | local Docker |
| [`deploy/ecs-express/claimclarity/`](deploy/ecs-express/claimclarity/) | ClaimClarity web UI | local Docker |
| [`deploy/ecs-express/glacierwatch/`](deploy/ecs-express/glacierwatch/) | GlacierWatch web UI | local Docker |
| [`deploy/ecs-express/trinetra/`](deploy/ecs-express/trinetra/) | Trinetra dashboard | **AWS CodeBuild** — no local Docker needed |
| [`deploy/ecs-express/trinetra-a2a/`](deploy/ecs-express/trinetra-a2a/) | Trinetra **A2A agent** | **AWS CodeBuild** |

The two CodeBuild-based paths are runnable entirely from CloudShell. The A2A
one deploys in two phases, because an agent card must advertise the address
peers call back on and a container cannot know what a load balancer answers on
— **read that directory's security section before exposing it**, since ECS
Express gives you a public HTTPS URL but not an authentication layer.

### A note on credentials in every deploy path

No build step ever receives a model credential. CodeBuild builds an image with
no key baked in; the key is injected only when the service is created or
updated, as a runtime environment variable. The scripts redact it even in
`--dry-run` output.
